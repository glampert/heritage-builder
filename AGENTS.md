# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, Codex, Cursor, etc.) when working with code in this repository.

## Project

2D isometric city builder in Rust (Pharaoh/Caesar-inspired), with custom renderers: OpenGL or Wgpu on desktop, Wgpu on web. Cargo workspace, edition 2024.

## Common commands

Desktop build/run (default feature set), on Rust 1.95 or later (egui's requirement):
- `cargo run -p HeritageBuilder` — debug
- `cargo run -p HeritageBuilder --release`
- `cargo build -p HeritageBuilder --release`

Command-line options (`cargo run -p HeritageBuilder -- --help` lists them all):
- `--map preset:N`, `--map empty:WxH` or `--load-save NAME` start in-game on that map; `--skip-home-menu` starts in-game on the map from `configs.json`.
- `--seed N` sets the random seed for new games and `--fixed-dt SECONDS` advances every frame by a fixed step. Together they make runs repeatable.
- `--default-configs` runs with the default configs from `assets/configs`, leaving out the user configs (see [Configs & singletons](#configs--singletons)); the Settings dialog's Ok then changes the configs for the run only. It still reads the player's profile.
- `--fresh-profile` starts from an empty player profile and never reads or writes `saves/user/profile.json`; in a replay it takes the place of the recording's profile (see [Realm and profile](#realm-and-profile)). CI passes it to every scenario run.
- `--window-size WxH` overrides the window size. `--render-api OpenGl|Wgpu` and `--app-api Glfw|Winit` override the backends from `configs.json` (desktop); `--render-api Wgpu` alone also picks Winit, the only app backend Wgpu runs on.
- `--screenshot-after-frames N --screenshot-out PATH` saves a PNG of frame N and quits: status 0 if it was written, 1 if not. Add `--screenshot-no-ui` to leave the UI out. A relative `PATH` is relative to the directory the game was started from, not `base_path`.
- `--script FILE` runs automation commands from a file and quits: status 0 if all succeeded, 1 if not, 2 if the file can't be read or has invalid lines. See [Script mode](#script-mode).
- `--automation[=PORT]` accepts commands from outside tools over localhost. See [Live control](#live-control).
- `--capture-input` starts with input capture on: the game ignores the real mouse and keyboard and takes simulated input. See [Simulated input and UI automation](#simulated-input-and-ui-automation).
- `--record FILE` records the run, and `--replay FILE` plays a recording back, then exits: status 0 if it ended in the same state, 1 if not. See [Record and replay](#record-and-replay).
- Unknown options exit with status 2. Options are declared in `engine::cli::ENGINE_CLI_OPTIONS` ([cli.rs](crates/engine/src/cli.rs)) and `game::launch::GAME_CLI_OPTIONS` ([launch.rs](crates/game/src/launch.rs)).
- Apply an option where its value is used. Don't write it into `GameConfigs`: the settings dialog saves the whole struct, as the user configs.

Headless Linux (CI, cloud agent sessions): install the packages from the CI Ubuntu job plus `xvfb`, then `LIBGL_ALWAYS_SOFTWARE=1 xvfb-run -a -s "-screen 0 1920x1080x24" cargo run -p HeritageBuilder -- <options>` runs the game on Mesa's software OpenGL. Without a sound device, audio init logs an error and the game runs silently.
- The Winit app backend (needed for `"render_api": "Wgpu"`) also needs `libxkbcommon-x11-0`, and Wgpu needs a Vulkan driver: `mesa-vulkan-drivers` provides lavapipe.
- To look at the game, take a screenshot with `--screenshot-after-frames` and read the PNG. `xdotool` can send real key presses to the window, e.g. `xdotool key F12`.
- `xvfb-run` runs its command with `2>&1`, so the log ends up in script mode's JSON output. For `--script`, start one server instead (`Xvfb :99 -screen 0 1920x1080x24 &`) and set `DISPLAY=:99`, as the CI `scenarios` job does.

Screenshots: PrintScreen or F12 saves `screenshots/<window title> <local date and time>.png` next to `saves/`; Shift leaves the UI out. A toast reports the file name. Code: `Engine::request_screenshot` ([screenshot.rs](crates/engine/src/screenshot.rs)) on top of `RenderSystem::request_capture` ([capture.rs](crates/engine/src/render/capture.rs)).

Console and automation commands: the [`] key opens the log viewer, whose input field runs commands, in any menus mode. `help` lists them with their parameters, and `help command=NAME` describes one. Lines take the form `name`, `name key=value ...` (values are JSON or plain text), `name {json}` or `{"method": "name", "params": {...}}`.
- Commands live in `crate::automation` ([automation/mod.rs](crates/game/src/automation/mod.rs)): one `CommandDef` table per area in `automation/commands/`, listed in `COMMAND_GROUPS`. The console, script mode and outside tools (through the engine's request queue, `engine::automation`) all run them.
- They run once per frame, right after the session command queue, where the world is unlocked and no `SimContext` is live. Commands that span frames return `pending(..)` and must keep ids, not references: a session load replaces the world.
- Parse params with `parse_params` into a `#[serde(deny_unknown_fields)]` struct, and validate before calling anything that panics or asserts on bad input (cell bounds, preset numbers, save names). The console only queues typed lines; never run commands from inside UI drawing.
- World edits go through `GameSession::with_sim_context` and the player's own paths (`TilePlacement::place`, `clear`, `place_road_segment`), which charge the tile's cost. `world.add_stock resources={...}` fills the storage yards that construction materials come from, and `world.add_population` a house. The world stats (treasury, population) are recounted on simulation steps and when a session is created or loaded, not after an edit; commands that place or report them call `refresh_world_stats` first.

### Script mode

`cargo run -p HeritageBuilder -- --script crates/game/tests/scenarios/smoke.jsonl` runs one command per line, each once the line before it has finished, and prints one JSON result line per command to stdout, then a summary line. Logs go to stderr in this mode, so `2>/dev/null` leaves only the results. It stops at the first failure unless `--script-continue-on-error` is given. Autosave is off, the player's profile is read but never written, and the Settings dialog's Ok changes the configs for the run only (the user configs are left alone, as in a replay or the smoke test).
- Lines use any console form; files usually hold `{"method": ..., "params": {...}}`. Blank lines and lines starting with `#` are skipped. Invalid lines and unknown commands are reported before anything runs.
- Results: `{"line": 3, "command": "world.place", "ok": true, "result": {...}, "frame": 12}`, or `"ok": false` with `"error": {"code": ..., "message": ...}`. The summary has `ok`, `succeeded`, `failed` and `skipped`.
- Assertions are commands: `assert.eq|ne|gt|ge|lt|le|exists` run a query command (e.g. `sim.state`) and compare the value at a JSON pointer (`path`). `wait.until` polls the same way.
- `assert.image golden=FILE` compares a screenshot with a PNG, pixel by pixel (`tolerance` per channel, `max_diff_pixels`); `update=true` saves the screenshot as the golden, and `path` saves it with a `-diff.png` beside it that marks differing pixels in red. Goldens only hold on the machine and render backend that made them, so CI checks state, not images. `--golden-dir DIR` resolves relative goldens against `DIR` (one directory per backend), and `--update-goldens` turns on `update` for the whole run.
- Repeatable runs: set `time.fixed_dt`, pass `--default-configs` and `--fresh-profile` so local user configs and the local profile can't change the run, start with `session.new_map`, `session.load_preset` or `session.load_save`, and use `time.fast_forward` for long stretches. `session.checksum` hashes the game state as a save would store it. Saves made in script mode, a recording or a replay leave the wall-clock save time out of their header (Saves, below), so they're the same on every run. Screenshots taken by commands (`assert.image`, `screenshot`) are encoded in the frame they're captured, unlike the hotkey's, so a script takes the same number of frames on every run and animations are at the same point in its screenshots.
- Sample scenarios live in [crates/game/tests/scenarios/](crates/game/tests/scenarios/): `smoke.jsonl` builds a settlement and checks settlers move in; `water_edges.jsonl` places land on water and checks the shore variations the water tiles pick; `calendar.jsonl` runs the calendar through a season and a year at 1× and 10× speed; `construction.jsonl` pays for a temple from a storage yard, waits out its construction site, and checks a cancelled site's refund; `renovation.jsonl` checks a house waits before renovating and upgrading, and keeps its level through the downgrade grace period; `goods.jsonl` runs a clay pit and the roof-tile kiln through a storage yard and pays a temple's roof tiles from it; `finance.jsonl` takes a small city's taxes, pays its wages and upkeep, runs it into debt and out again, and sets the tax level and wage in the finances dialog; `risks.jsonl` builds up fire and collapse risk, slower beside a well, sets risks by hand and turns them off, burns a storage yard down and collapses another, clears part of the rubble, burns a house on a vacant lot down to rubble on grass, has one fire watcher put out a yard's fire and then a house's off the road, and has a sick house spread disease risk, lose a resident after the grace period and be cured by a hospital's medic; `determinism.jsonl` must print the same checksum and write the same `saves/determinism.json` on two runs with the same `--seed`; `ui_new_game.jsonl` (a Blank map from Custom Game) and `ui_build.jsonl` play through the menus and HUD, and `ui_dev_menus.jsonl` through the developer editor's menus, the tile inspector (its risk buttons included), the debug windows and the log viewer's console; `minimap.jsonl` checks the minimap follows placements and clicks its lens and tool buttons; `strings.jsonl` checks the localized strings: `text.*`, a popup's text from its keys, the inspector's descriptions and no missing key; `ui_sounds.jsonl` checks the UI sound roles that buttons, a checkbox, a dropdown, a slider, dialogs, a popup, the palette, a construction toast, minimap alerts and debt toasts play, and that a realm switch rebuilds two stacked dialogs from the new skin, keeping the stack and their sounds; `profile.jsonl` edits the player's profile with `profile.set` and `profile.reset` and checks what follows, the home menu's realm included; `ui_skins.jsonl` opens the developer Skin Gallery in each realm, checks its layout, drives its controls (toggle, checkbox, slider, dropdown, step selectors, tab bars, list rows, icon buttons), reads what its data widgets report, opens its popup and saves screenshots to `out/ui_skins/`; `ui_menus.jsonl` visits the home menu, About and the campaign picker in each realm (the profile, through `profile.set`, picks the realm and fills the campaign row), Custom Game in each realm (its locked realms, maps, preview and options) and starts a preset and a blank custom game, checking the session, a save and a load, every Settings tab in each realm (`ui.realm`), cancels a change, keeps changes on each tab through a realm switch and a skin reload, commits them with Ok (`config.get`), opens the settings kinds on their tabs and restores the defaults, starts a campaign at its next mission from Home and from the picker, opens the in-game Game menu, its dialogs and its Quit and Exit popups in each realm, saves through its Save, saves and quits through the popup, continues the last save, saves two games in the Load / Save dialog, reads their rows and preview in each realm, deletes one through its popup and loads the other, then deletes Continue's save over the home menu (it needs the sample saves extracted, deletes the saves it writes, and stops at once if `saves/autosave.json` exists, since Save and quit writes the autosave's slot), and saves screenshots to `out/ui_menus/`. `ui_world_map.jsonl` opens the world map in a Campaign I game from the minimap and the Game menu, in each realm (`ui.realm`), checks the top bar, markers and the side panel of cities it selects, zooms with the wheel, pans at the map's edges (`WorldMap/map/right`), checks the layout at 100%, 200% and 75% UI scale, then starts the hidden test campaigns' missions (`session.start_mission`) and checks each realm's choice box and sites, the popup a site asks in, and that Begin starts the B mission (`session.state`'s `campaign/campaign_id` and `mission_id`) and records the choice in the profile, and saves screenshots to `out/ui_world_map/` (it needs the sample saves extracted); `ui_snapshot.jsonl` visits every screen, retail and developer, and at each lists the widgets (`ui.tree` without rects) and checks a golden screenshot; its header shows how to make and compare goldens per backend. It isn't run in CI, which has no goldens. The window size is part of the game state (the camera's viewport), so give `--window-size` when comparing runs: macOS shrinks a window that doesn't fit the screen by a pixel more or less from run to run. Debug and release builds give the same checksums.

### Live control

`hb-ctl` ([crates/tools/hb-ctl](crates/tools/hb-ctl/)) drives a running game through its automation server, so there's no socket code to write:
- `cargo run -q -p hb-ctl -- launch --map preset:2 --fixed-dt 0.016667` builds the game, starts it with `--automation=0`, waits until it answers, and prints its pid, port and log file (`logs/game-<pid>.log`). Arguments other than `--release`, `--no-build` and `--wait SECS` go to the game: add `--fresh-profile` so the run neither reads nor writes the player's profile.
- `hb-ctl call world.place tile=small_well 'cell=[5,5]'` (or a JSON object) prints the result as JSON; status 1 if the game reports an error, 2 if it can't be reached. `hb-ctl commands [NAME]` lists the commands.
- Also `hb-ctl screenshot out/x.png [--no-ui]`, `logs [--follow] [--level L]`, `script FILE` (same output as `--script`) and `quit`. Options go before the command: `--pid PID` picks an instance when several run, and `--dir DIR` points at a game directory other than the repository root.
- Protocol: newline-delimited JSON-RPC 2.0 on 127.0.0.1 ([server.rs](crates/engine/src/automation/server.rs)). A connection first sends `auth` with the token from `logs/automation.json`, which also holds the pid and port (`logs/automation-<pid>.json` names one instance; both are removed on exit). Responses carry the frame they finished on, and errors carry the game's code in `error.data.code`. The server answers `logs.subscribe` / `logs.unsubscribe` itself and sends notifications: `log`, `session.changed` and `panic`.
- Every desktop panic writes `logs/crash-<timestamp>.txt` with the message, backtrace, frame and recent log records. `debug.panic` crashes the game on purpose to test this.
- MCP: `hb-ctl mcp` serves the commands as MCP tools over stdio, and the project's [.mcp.json](.mcp.json) registers it with Claude Code as `heritage-builder`. Tools: `game_launch` (quit again when the client disconnects), `game_connect`, `game_call`, and one per command with dots as underscores (`world_place`), listed once a game is connected. `screenshot` returns the image, at window-point resolution unless `scale` says otherwise.
- The [drive-game skill](.claude/skills/drive-game/SKILL.md) has recipes for launching, driving, screenshots and debugging.

### Simulated input and UI automation

- `input.move|click|drag|key|type|scroll` play gestures on a virtual mouse and keyboard over several frames, since input is polled once a frame: a click is a hover, a press on the next frame and a release on the one after. Targets are window points, or map cells (the camera centers on the cell first unless it's in the middle of the screen). The timeline is [automation/input.rs](crates/engine/src/automation/input.rs); `VirtualInput` lives in [app/input.rs](crates/engine/src/app/input.rs).
- Input capture: while on, the `InputSystem` reports the virtual state, real input events are dropped (except quitting and resizing), and cursor confinement stops moving the real cursor. Gestures turn it on; `input.capture on=false` turns it off, and so does a real Shift+Esc. Script mode and `hb-ctl launch` start with it on (`--capture-input`). A badge says so on screen, but not in screenshots.
- `ui.tree` lists the widgets drawn last frame: path (menu and labeled-group labels, then the widget's own), kind, rect in window points, enabled, value, and `visible: false` for one scrolled out of its window's view. Widgets record themselves in their `draw` through `UiSystem::record_widget` ([ui/registry.rs](crates/engine/src/ui/registry.rs)); the registry is off until a `ui.*` command turns it on. `ui.tree` works as an `assert.*` query once it's on.
- `ui.tree fields=[...]` keeps only the named fields of each widget, e.g. `["path", "kind", "value"]` for a listing that doesn't change with layout.
- The realm UI's retained widgets record these kinds: `tab_bar` (value: the selected tab's label; unlabeled, `<menu>/tab_bar`) and a `tab` per tab (value: selected), the selected tab's label in its contents' paths (`MainSettings/Game/Autosave`); `toggle` (bool); `step_selector` (value: the current step's label) with a `step` per segment, or `Previous`/`Next` buttons, under its label; `menu_entry` (`UiMenuItem`; value: `subline`, `selected`; `menu_item` is the developer menu bar's); template list rows as `list_item` under their list (by title; value: `selected`, `subtitle`, `right`, `right_subtitle`; its rect the part the list shows); `icon_button` (value: selected); `image` (value: `fit`), `key_values` (value: `[[label, value], ...]`), `table` (value: `columns`, `rows` and, with a status column, `status`), `meter` (value: `value`, `max`), `rich_text` (value: its text; labeled by its text unless given a label) and `card` (`UiCard`; value: `selected`; its widgets' paths take its label). `UiColumns` records nothing itself.
- Each retail menu also records its content area (kind `menu_content`, path: the menu's label, e.g. `Home`), the rect its widgets are meant to stay in. `ui.click`, `ui.hover` and `ui.set` find it by its full path only, so it can't shadow a widget of the same name; an unlabeled widget straight in a menu, which would take the menu's path, goes by its kind instead (`LoadOrSaveGame/item_list`).
- `ui.layout_issues` lists the widgets drawn last frame that fall outside their menu's content area (`menu_content`) or overlap a sibling, with a `count`; widgets scrolled out of view aren't checked, nor, in a menu whose contents scroll (its `menu_content` value is `{"scrolls": true}`; a menu with a size records `{"scrolls": false}` while its contents fit), one its top or bottom edge cuts as long as it fits the menu's width: `ui_snapshot.jsonl` asserts it's 0 on every retail screen. A menu lays its contents out in its inner rect, its rect minus its content insets (`UiMenu::with_content_insets`, or `with_panel`'s), in whole points with no upper limit, and records that rect as its `menu_content`; dialogs scroll their contents when they don't fit it. A labeled `UiFrame` records its inner rect as a `menu_content` too (`WorldMap/panel`), which its widgets are held to. Two `map_marker`s may overlap (cities close on a map).
- `ui.reload_skin` reads the UI skin files again (`assets/configs/ui/skins/`, e.g. after editing one) and rebuilds the dialogs and HUD with them from the next frame; the current skins stay if one fails to load. Loaded images stay cached, so an image changed under the same path needs a restart; on web, which reads a file once, it only rebuilds. `ui.reload_styles` reads the developer UI's style file again (`assets/configs/ui/styles/dev.json`), keeping the skins' styles; on web it's an error, since the files can be read only once. `ui.realm realm=...` shows that realm's skin in the same frame.
- `ui.click path=...` takes a full path, the end of one ("Custom Game"), a label or a tooltip, and waits up to 30 frames for the widget to appear. It moves the cursor onto the widget first, following it if it moves (a window resizing to new contents), and fails if the widget doesn't report it's hovered, i.e. a menu or window covers it. A dev-menu widget scrolled out of view is scrolled into view first; any other such widget fails. It finishes once the click's result has drawn once. `ui.hover path=...` does the same without the click and leaves the cursor there, e.g. to show a tooltip. `ui.set` sets checkboxes, toggles, sliders, number and text inputs (an integer field's step buttons are `<field>/-` and `<field>/+`, disabled at the ends of its range), dropdowns, lists, tab bars and step selectors (a tab's or step's label or index) through the widget's own update callback, scrolled out of view or not, but not read-only ones. A dev-menu text input takes the text even while it has keyboard focus. `dialog.list|current|open|close` wrap `menu::dialog`; `dialog.open` closes every other dialog in the stack but the home menu's own, which stays open under the new one, as its buttons leave it.
- Dialogs ([menu/dialog/mod.rs](crates/game/src/menu/dialog/mod.rs)): each is its own window, so its widgets' paths start with its own label, its `DialogMenuKind` name, wherever it was opened from: `CustomGame/Start`, `MainSettings/Game/Autosave`, `FinancesManagement/Tax Level`, `LoadOrSaveGame/item_list`. The Settings dialog ([dialog/settings/](crates/game/src/menu/dialog/settings/mod.rs)) is one dialog, `MainSettings`, with tabs `MainSettings/Game|Sound|Graphics|Controls` (`MainSettings/tab_bar`): `dialog.open` of `GameSettings`, `SoundSettings` or `GraphicsSettings` opens it on that tab (switches to it if it's open), and only `MainSettings` shows as open. A row per setting, `MainSettings/<Tab>/<label>` (a `toggle`, `slider` or `dropdown`; settings the engine reads at startup say so in their label: `MainSettings/Graphics/Window mode (after a restart)`), the read-only `MainSettings/Controls/Key bindings` table, and `MainSettings/Restore defaults|Cancel|Ok`. Its pending values and tab live outside its widgets, so a rebuild (`ui.realm`, `text.language`, `ui.reload_skin`, or a window size change, which builds it again for the new size) keeps them; they're read from `GameConfigs` when it opens. Ok writes the changed ones (check with `config.get`), applies the volumes, texture settings, autosave and language at once (the UI scale from the next frame) and saves the user configs; Restore defaults reads `GameConfigs::defaults()` (assets/configs). The Load / Save dialog ([dialog/load_save.rs](crates/game/src/menu/dialog/load_save.rs)) is one dialog, `LoadOrSaveGame`: `dialog.open` of `LoadGame` or `SaveGame` opens it in load or save mode (its primary button, and whether it starts on the newest save or a new name), and `dialog.current` and `dialog.list` report `LoadOrSaveGame` (`LoadGame` and `SaveGame` never show as open). A row per save (`LoadOrSaveGame/<save>`, newest first), the field `LoadOrSaveGame/Save as` (a row picked fills it; a save's name typed picks its row), `LoadOrSaveGame/preview` (the thumbnail) and `LoadOrSaveGame/details` (key values), and `Delete`, `Cancel`, `Save` and `Load`; popups `Overwrite Save Game Popup/Yes|No` and `Delete Save Game Popup/Delete|Cancel`. It reads the saves' headers when it opens and is built again when the saves change (`save_header::revision`: a save, a thumbnail, a deletion) or the window's size changes its scale, keeping what's picked. Save is disabled in the home menu; saving over a name that differs only in case asks in the Overwrite popup too. The Custom Game dialog ([dialog/custom_game.rs](crates/game/src/menu/dialog/custom_game.rs), the game side in `crate::custom_game`): the lists `CustomGame/Realm` (a row per realm, `CustomGame/Realm/Kambara`, disabled with "Start Campaign II to unlock" until one of its campaigns is playable or the profile's `custom_realms` has it; `ui.click` on one fails, `ui.set` leaves the pick) and `CustomGame/Map` (a row per map in `assets/configs/game/maps.json` that can be played now, its size in `right`), the Blank map's `CustomGame/Width|Height|Terrain` (step selectors, shown only while it's picked), `CustomGame/preview` and `CustomGame/details` (Size, Water, Woodland, Trade partners, Hazards), the dropdowns `CustomGame/Starting date|Goals|Starting treasury`, `CustomGame/Difficulty`, the toggles `CustomGame/Seasons and floods|Fires and collapses|Raids and invasions|Fast construction` (the first and third disabled, with a tooltip) and `Cancel|Start`. What's picked lives outside its widgets (`custom_game::STATE` in the dialog), read afresh when it opens; it's built again when the realm changes, the Blank map is picked or left, or the window's scale changes. About ([dialog/about.rs](crates/game/src/menu/dialog/about.rs)): the crest (`About/crest`), headings (title, campaign, studio line, a heading per credit section: `About/ART To be announced`, in two columns), the quote, version and `About/Back`. The in-game Game menu ([dialog/main_game.rs](crates/game/src/menu/dialog/main_game.rs)): menu entries `MainGame/Resume|Save|Load|World map|Settings|Quit to menu|Exit game`, and `MainGame/place` and `MainGame/last_saved` (rich text: the mission or custom game, and "Saved N minutes ago" or "Autosaved ..." from `GameSession::last_saved`, at the bottom; both followed each frame it's drawn, so a save through its own Save shows once Load / Save closes). Quit to menu and Exit game open `Quit Game Popup` and `Exit Game Popup` (`Cancel`, `Save and quit` or `Save and exit`, `Quit` or `Exit`); saving first closes the popup and is `GameLoop::save_and_then`: it writes the autosave's slot at the start of the next frame and leaves once that save's thumbnail is written; a failed save, Cancel, a direct Quit or Exit, or another session drops it. Both dialogs scale their contents with the window and are built again when its size changes (`DialogMenuKind::scales_with_window`). The world map ([dialog/world_map/](crates/game/src/menu/dialog/world_map/mod.rs), `WorldMap`, full screen; in game only: `dialog.open` fails in the home menu): opened by the minimap's World map tool and the Game menu's `MainGame/World map` entry (a stopgap until the HUD's button, Phase 5; the intermission's comes in Phase 3), which closes the Game menu, so `WorldMap/bar/Return to the city` goes back to the city either way. It shows the map of the UI realm's campaign (`world_map::screen_campaign`: the mission's when it's that realm's, else the realm's first visible campaign), laid out as `world-map-<realm>.jpg` on the window scaled from 1920 × 1080 (`screen_scale`; its text takes the UI scale back out, so 75% and 200% look the same). Paths: `WorldMap/bar/title|subtitle|date|season|coin|treasury|Return to the city`; `WorldMap/map` (kind `map_view`, value `zoom`, `centre` in map units, `fit`, `max_zoom`; `ui.set` takes `zoom`/`centre`) and its edge strips `WorldMap/map/left|right|top|bottom` (kind `map_edge`: `ui.hover` one to pan); a marker per city and next-mission site, `WorldMap/<name>` (kind `map_marker`, value `id`, `kind`, `owner`, `player`, `selected`, `current`, or `site` and `mission`; `ui.click` selects a city); `WorldMap/panel/emblem|name|subtitle|relations|relations_meter|route|route_detail|They sell|They buy|request/title|request/goods|note|Set trade limits|Send a gift` (the buttons disabled, tooltip "Coming with trade", until M10); `WorldMap/legend` (kind `canvas`, value the entries' texts). The next mission's choice (the step after the one being played offers `choices`): its A/B sites (`map_marker`, value `site`, `mission`) and the choice box in the view's corner where the world file's `choice_box` puts it at the fit, whatever the zoom (`WorldMap/choice`, kind `choice_box`, value `title`, `subtitle`, `mission`, `open`), its sites' names in it (`WorldMap/choice/Vân Cảng`, kind `choice_option`); clicking a site or its name opens `Choose Site Popup` (`Cancel`, `Begin the mission`), and Begin starts that mission (`home::start_campaign_mission` over `campaign::start_mission_if_loadable`, through the session command queue) and records the pick (`Profile::choice_made`); while the campaign's mission being played is unfinished, or another game is being played (a custom game, another campaign's mission: `value.open` false), a site opens `Finish Mission Popup` (`Ok`) instead. The skin's `world_map` block draws the box (`choice_box`, the `choice_title` and `choice_subtitle` text looks, the `choice_box_*`, `choice_line` and `choice_hover` colours). MissionComplete's Next Mission opens the world map instead of the next mission when the next step offers a choice and the map shows that campaign (not under a `ui.realm` override to another realm's). ### Record and replay

`--record FILE` writes the run as JSON lines as it goes, and `--replay FILE` plays it back, e.g. to reproduce a bug report. Code: [engine automation/recording.rs](crates/engine/src/automation/recording.rs), driven from `Engine::begin_frame` and `Engine::finish_run`, and the game's part in [game automation/recording.rs](crates/game/src/automation/recording.rs).
- A recording holds what the game can't recompute: each frame's time step, the real mouse and keyboard (sampled once a frame, below input capture, so simulated input comes from the replayed commands), and the automation commands from scripts and outside tools, on the frames they started. Console commands are left out, since the replayed typing runs them again.
- The header holds the command-line options, the window size, the input capture state, and the game's version, autosave setting (and whether the Settings dialog may turn autosaving on), `GameConfigs` and the player's profile (a replay uses it unless `--fresh-profile` is given, and never writes the profile file). Options for run modes that the recording covers (`--script`, `--automation`, `--screenshot-*`) are left out. The last line holds the frame count and the final state's checksum, as `session.checksum` hashes it.
- A replay runs with the recorded options, window size and configs. Options given with `--replay` come after the recorded ones and win, so `--automation` lets `hb-ctl` watch it, but commands sent then change the run. Real input is ignored, except quitting and Shift+Esc, which stops the replay and gives the input back. At the end, the replay compares the frame count and checksum: exit status 0 if they match, 1 if not.
- Each line is written as it happens, so a crash leaves a recording without its last line. Replaying it crashes the same way, or gives the input back after the last recorded frame.
- Saving changes the game state: `pre_save` resolves pending spawns early. That's why a replay autosaves exactly when the recorded run did, and why `session.checksum` counts as a save.
- Limits: the window size and display scale must match the recording, and warnings say when they don't. The window size is part of the state, so record with `--window-size` if the window might not fit another screen. A replay can't resize the window. `--load-save` needs the same save file. A replay repeats the run's side effects: saves (with their thumbnails), screenshots and autosaves.

Every crate exposes `desktop` (default) and `web` features that fan out through the workspace. When touching `common`, `engine`, or `game`, keep both targets compiling.

## Runtime architecture

Entry point flow: `launcher::main` → `engine::runner::run::<GameLoop>()` → platform `Runner` (desktop synchronous loop vs. browser `requestAnimationFrame`) → `GameLoop::start` → per-frame `GameLoop::update`.

Key types:
- `engine::Engine` — singleton holding platform, renderer, UI (egui), sound (Kira), save system. Passed by `&mut` into game code each frame.
- `engine::runner::RunLoop` trait — implemented by `game::GameLoop`. The engine drives it; `GameLoop` does not own the main loop.
- `game::GameLoop` ([game_loop.rs](crates/game/src/game_loop.rs)) — top-level game state holder. Owns the boxed `GameSession` plus command queue, autosave timer, and frame stats.
- `game::session::GameSession` ([session.rs](crates/game/src/session.rs)) — fully serializable game state: camera, tile map, world, simulation, systems. Save/load round-trips through this.
- `game::sim::Simulation` ([sim/mod.rs](crates/game/src/sim/mod.rs)) — core logic. Deterministic: owns a PCG64 RNG seeded from `SimConfigs::random_seed`. Has separate `update_timer` (active) and `paused_update_timer` (paused-state ticks). Fixed-step ticks: the sim runs on its own timer, not every frame — but unit navigation does run every frame for smooth movement.
  - Time: a frame advances the simulation by its time step times the speed, once (`Simulation::advance_clocks`). The world step's delta is the simulated time since the last step, the frame it fires on included, so the world, the game systems, the calendar and `elapsed_secs` all count the same time at any speed; `cargo test -p game --test game_time` checks it at 1×, 2× and 10×. `elapsed_secs` is runtime only (automation waits on it); the calendar is the saved clock.
  - `game::sim::GameCalendar` ([sim/calendar.rs](crates/game/src/sim/calendar.rs)), saved in `Simulation` and read through `SimContext::calendar()`: the date (day, month, World Year), the season (wet or dry, from the month) and the era. `SimConfigs::seconds_per_month` (60) and `days_per_month` (30) set its pace; it stores whole months elapsed so they can change without moving a save's date. Its `CalendarSettings` (start year and month, wet months, eras) come from `SimConfigs::calendar` outside a campaign, and from the mission's `calendar` and the campaign's `eras` in `campaigns.json` when a mission starts (`campaign::active_mission_calendar`).
  - Calendar events: a world step that crosses into a month calls `GameSystem::on_new_month`, then `on_new_season` and `on_new_year` when they apply, after the step's update, and logs them on the `calendar` channel. `calendar.set` moves the date without events; `sim.state` and `session.state` report it under `date` (wait for a date with `wait.until` on `/date/ordinal_month`, year × 12 + month − 1). The top bar shows the date and season.
  - `SimConfigs::seconds_per_day` (600) is not a calendar day: it's the rate unit of house consumption (`HouseConfig::consumption_rates`, units per resident per 600 s). Moving rates to calendar months is left to M13's balance pass.
- `game::sim::SimContext<'game>` and `SimContextMut<'game>` ([sim/context.rs](crates/game/src/sim/context.rs), [plan](docs/plans/simcontext-refactor.md)) — what simulation code sees of the World, TileMap, finances, calendar, risks, path search, unit tasks and RNG.
  - **`SimContext` is read-only.** The world step gets one (`World::update`, the building, unit and prop updates, `GameSystem::update` and its calendar events, unit task runs), so anything that changes the world, the tile map or the simulation's state goes through `SimCmds`, which the step's code receives separately. Only the RNG, the unit task manager and the path search may change through it: they're shared resources, not world edits.
  - **`SimContextMut` adds the mutable API** (`world_mut`, `tile_map_mut`, `finance_mut`, `risks_mut`, `cmds_mut`, the `*_mut` lookups, placement) and derefs to `SimContext`, so read-only helpers take `&SimContext` and serve both. Everything outside the world step gets one: `SimCmds` and their callbacks, unit navigation, spawning and despawning, the player's tools, automation, debug UI. `BuildingContext` and `BuildingContextMut` are split the same way: the archetype's `update` gets the first; `spawned`, `despawned`, `visited_by` and `draw_debug_ui` the second.
  - Code shared by both paths takes `&SimContext` and queues its changes, with a `*_now` twin on `&SimContextMut` where something needs them at once (`Building::ignite` / `ignite_now`, `start_outbreak` / `start_outbreak_now`).
  - **Lifetimes, raw pointers.** Both hold `RawPtr`s, because the world's update iterates its objects mutably while they read the world through the context; the `'game` lifetime ties a context to the borrows it was made from. Outside `sim/`, build one with `Simulation::new_sim_context` (or `GameSession::with_sim_context`, `GameUiContext::new_sim_context`), which borrows the simulation, world and tile map for as long as it lives. Only `Simulation` builds contexts over parts it's using itself (`unsafe` `from_raw`).
- Goods ([goods plan](docs/plans/goods.md)): `ResourceKind` ([sim/resources.rs](crates/game/src/sim/resources.rs)), a `u64` bitflag whose bit is the good's index in per-good arrays. Saves, configs and automation spell a good by its flag name (`RoofTiles`); the player reads `display_name()` ("Roof Tiles"). To add a good:
  1. Add the flag anywhere in `ResourceKind`, keeping the bits contiguous from 0 (renumber the ones after it; a compile-time check enforces it), and add it to its group (`foods()`, `consumer_goods()` or `raw_materials()`): houses accept every food and consumer good, and the world stats count goods by group.
  2. Configs in `assets/configs/buildings/configs.json`: a producer in `producer_configs` (`production_output`, `resources_required` for inputs), the storage that takes it (`resources_accepted`), and, for what houses need, the market's `resources_required`, a house level's `resources_required` and `house_config.consumption_rates`. A construction material goes in tile defs' `materials` (at most `MAX_CONSTRUCTION_MATERIALS`, 4).
  3. A new producer's art comes from the tile generator: a catalog entry with its `sector`, then `tilegen.sh` (see `crates/tools/blender-tile-generator`).
  4. No save-version bump: saves name goods, and stocks take their config's goods on load. Run `--smoke-test-saves` to confirm, and add the good to a scenario, as `goods.jsonl` does for roof tiles.
- Finance ([finance plan](docs/plans/finance.md)): `game::sim::finance::Finance` ([sim/finance.rs](crates/game/src/sim/finance.rs)), saved in `Simulation` and read through `SimContext::finance()`.
  - **One balance:** all of the city's gold, signed, so negative is debt. Tax offices hold no gold: a collector's patrol pays into the treasury when it returns (`earn(Taxes)`). Placement charges and refunds go through `spend` and `refund(Construction)`. Cheats, debug tools and `finance.set balance=` use `add_unrecorded` and `set_balance_unrecorded`, which leave the accounts alone.
  - **Affordability:** `Finance::can_afford` and `shortfall`, not the world stats. A treasury in debt can pay nothing.
  - **Monthly charges:** wages (employed workers times the yearly `wage`) and upkeep (a tile def's `upkeep`, gold per year, for finished buildings only) are charged a twelfth at a time at each month's end, with the remainder carried (`Finance::on_calendar_events`, after a world step's `SimCmds`).
  - **Debt clock:** `months_in_debt` counts month-ends in debt in a row; at `FinanceConfigs::debt_limit_months` (12) the debt is overdue (`is_debt_overdue`). Notices go to the `finance` log channel and become toasts (`GameLoop::notify_finances`).
  - **Tax level:** `TaxLevel` (None, Low, Normal, High, Harsh) pays `FinanceConfigs::tax_level_percent` of the houses' base tax (0, 50, 100, 150, 200). A mission's `finance` block in `campaigns.json` sets the starting gold, tax level and wage (`Finance::start_mission`).
  - **Accounts:** `this_year` and `last_year` hold a total per `LedgerCategory` (`Taxes`, `Construction`, `Wages`, `Upkeep`); the new year moves them.
  - **To add a category:** add it to `LedgerCategory` (any position) with its `name()` and, for income, `is_income()`; record through `earn` or `spend`; and add its line to the finances dialog. No save-version bump.
  - **Automation:** `finance.state` reports it all, and `finance.set` takes `tax_level`, `wage` and `balance`. `sim.state`'s `gold` is the balance.
- City risks ([city-risks plan](docs/plans/city-risks.md)): each building's fire and collapse risk, and a house's disease risk, `building::risks::BuildingRisks` ([building/risks.rs](crates/game/src/building/risks.rs)), saved on `Building`.
  - **Build-up:** 0 to `MAX_RISK` (100), in `Building::update`, at the rates in its building config's `risks` block (points per calendar month; `BuildingConfig::risk_rates`, a house's from its level). Sites and buildings without the block build up nothing. `Building::risk_rates` is what they build up at now.
  - **Jitter:** each building's rates are scaled by a factor (`RiskConfigs::rate_jitter`, ±25%) hashed from its base cell and kind (`common::hash::splitmix64`), recomputed on spawn, on load and when the base cell moves (a house that expands), never saved and never drawn from the RNG.
  - **Water:** a building that a small or large well reaches builds up fire risk at `near_water_fire_scale` (0.5) of its rate. It checks every `water_check_secs` (10) with `has_access_to_service`, a path search.
  - **Visits:** a walker whose patrol came from a `FireWatch` resets the fire risk, one from a `BuildersGuild` the collapse risk, one from a `Hospital` (a medic) the disease risk (`risks::risk_reset_by`, checked in `Building::visited_by` before the archetype). Walkers are told apart by their patrol's origin, as tax collectors are: the builder is a `Peasant`, the fire watcher a `FireWatcher` (the guard recoloured by `crates/tools/unit-recolor`). Both buildings' patrols visit every building (`ServiceConfig::visits`, `PatrolVisits::AllBuildings`; other services visit houses).
  - **Dispatch:** a staffed fire watch, or hospital, whose runner slot is free (neither has stock, so the slot is spare) sends a walker straight to the nearest burning building, or sick house, within its `effect_radius` (`ServiceBuilding::send_out_responder`, `UnitTaskRespond` with its `Emergency`, `Fire` or `Outbreak`, in [unit/task/respond.rs](crates/game/src/unit/task/respond.rs)). He walks over any land, road or not (`RESPONDER_NODE_KINDS`), to a cell next to it (`SimContext::find_path_next_to`, which unlike `find_nearest_buildings` never steps on water next to a building), makes his visit, goes on to the nearest other such emergency within that radius of where he stands, and walks home once none is left. Every building in reach answers, so two may send someone to the same one. Patrols keep to the road.
  - **Switch:** `sim::risks::CityRisks` (saved in `Simulation`, `SimContext::risks()`) turns risks off for a game, and disease alone (`is_disease_active`); a mission's `risks` block in `campaigns.json` sets them (`enabled`, `disease`; `GameSession::start_mission`). It also counts the game's deaths from sickness. The `no_city_risks` cheat stops them too; the test harness turns it on and `tests/risks.rs` off, and long scenarios set it.
  - **Collapse:** a collapse risk at 100 queues `SimCmds::destroy_building`. **Fire:** a fire risk at 100 sets the building burning (`Building::ignite`, `TileFlags::Burning`) for `burn_secs` (30). A burning building skips its archetype's update, takes and hands out no goods, isn't operational, and adds `spread_per_sec` (5) fire risk a second to each building next to it; then it burns down. Only a finished building with that rate in its config can burn or collapse (`can_catch_fire`, `can_collapse`). While risks are off a fire waits.
  - **Fire watchers:** a burning building turns away every walker but a fire watcher, whose visit puts the fire out (fire risk 0, unharmed).
  - **Destruction** (`building::destruction::destroy_building`): a delayed `SimCmd` (it runs after the step's other commands, so their visits still find the building), then a despawn as the player's demolition, without refund. Rubble covers the footprint (`tile::rubble`; a house's vacant lots go back to grass or dirt first, since nothing else can stand on a lot), the world stats are recounted at once (the building's goods are lost), and `risks::notify` queues the notice that `GameLoop::notify_risks` shows as a toast. Deferred building commands naming a building that's gone are skipped. Fires and destructions raise minimap alerts.
  - **Rubble:** a `TileKind::Rocks` tile per cell whose variation is its neighbour mask; see [.claude/rules/terrain-tiles.md](.claude/rules/terrain-tiles.md).
  - **Disease** (houses only; house levels' `risks.disease`): the rate is the level's times the jitter, how full the house is (`Building::fullness`) and its needs (`BuildingRisks::disease_needs_factor`: more without a well or food, half with an apothecary in reach, checked with the well on `water_check_secs`). A disease risk at 100 sets nothing off: every `disease_check_secs` (10) a house with people rolls the simulation's RNG for an outbreak (`risks::outbreak_chance`, `outbreak_chance_at_max` × (risk / 100)² a month). A sick house (`OutbreakState`, `TileFlags::Diseased`, drawn tinted with a `sickness_1x1` overlay) takes no settlers, doesn't grow, renovate, upgrade or merge (it knows through `BuildingContext::has_outbreak`), spreads disease risk to houses within `disease_spread_cells`, and after `death_grace_secs` loses a growing share of its residents every `death_interval_secs` (`HouseBuilding::lose_residents_to_disease`: no walker). A medic's visit cures it (risk 0); an empty one ends its outbreak at half risk. Notices tell the outbreak and its deaths at the end.
  - **Automation:** `risks.state` (switches, counts, riskiest buildings, fires, outbreaks, deaths), `risks.set` (`enabled`, `disease_enabled`, or a building's `fire`, `collapse` and `disease` by `cell`), `risks.ignite`, `risks.collapse` and `risks.infect` by `cell`, `world.building_at`'s `risks`, and `world.add_population` to fill a house at once. The developer Tile Inspector's `Building/Risks` section shows the raw values, with `Set On Fire`, `Collapse` and `Start Outbreak` buttons when the building can; the collapse is queued (`destruction::request`) and runs at the start of the next frame (`Simulation::update`), since the inspector is drawing the building.
- Building costs ([construction plan](docs/plans/construction.md)): a tile def's `cost` (gold) and `materials` (e.g. `{ "Wood": 6, "Bricks": 8 }` in `tile_set.json`) are charged only by the player's placement paths: `Spawner` charges nothing unless `set_subtract_tile_cost(true)`, so `SimCmds` spawns (settler houses) and presets are free. Materials come from the city stock, `world::city_stock::CityStock`: every storage yard's slots, staffed or not, taken in pool order. Undoing a placement refunds gold and materials (into any yard with room); demolishing refunds nothing.
  - Construction sites: the player's placements (`TilePlacement::place` with `ConstructionMode::Site`: the HUD, `world.place`, undo/redo) start a building as a site for its tier's time (`TileDef::construction_tier()`: Instant, Decorative, Basic, Civic, Grand; durations and `time_scale` in `SimConfigs::construction`). A site is `Building::construction` (`building/construction.rs`, saved): `Building::update` only advances it, and it's not operational, holds and takes no goods, refuses visitors, counts for nothing in the stats, and is skipped by service coverage, settlers and the city stock. On completion a deferred building update clears its tile flags, moves in a settler house's residents, and queues a notice (`construction::notify_completed`, not for settler houses) that `GameLoop` turns into a toast and a sound. Toasts are left out of captured screenshots. Clearing or undoing a site refunds exactly what it took; redo, or undoing the clear, places a new site and charges again.
  - Presets, `SimCmds` spawns and the developer editor place finished buildings (the `build_sites_in_editor` cheat makes the editor build sites). A settler's house is a site of `house_build_secs`. A custom game with fast construction on multiplies every duration again by `SimConfigs::construction.fast_construction_scale` (0.25; `custom_game::construction_time_scale`, `session.state`'s `custom_game/construction_time_scale`). The `instant_construction` cheat finishes everything at once; the test harness turns it on, and `tests/construction.rs` turns it off. Script mode doesn't, so a scenario that places a storage yard waits for it (`time.fast_forward sim_secs=16`) before stocking it.
  - House upgrades are renovations (`HouseUpgradeState::advance_timers`, [building/house.rs](crates/game/src/building/house.rs)): once a house meets the next level's needs for `HouseConfig::renovation_delay_secs` (30) in a row, it renovates for `renovation_secs` (10), then upgrades if it still meets them. A house that stops meeting its own level's needs downgrades only after `downgrade_grace_secs` (40) in a row. Checked every `upgrade_update_frequency_secs` (10). A forced level change (the inspector's setter, `SimCmd` upgrades) resets the timers. `world.building_at` reports them under `house`, and `world.add_stock cell=[x,y]` stocks one building, e.g. a house's food.
  - The renderer only sees tiles, so a site reaches it as `TileFlags::UnderConstruction` plus a stage (0–3) in `ConstructionStage0/1`, set by `building::set_construction_tile_flags`. `TileMapRenderer::draw_tile` ([tile/rendering.rs](crates/game/src/tile/rendering.rs)) draws `scaffold_NxN` for the footprint instead of the building, its frame `stage<N>`. A renovating house (`TileFlags::Renovating`) draws lightly tinted with `renovation_NxN` over it. Both are anchored like a building of that footprint at their own draw size. Without art for a size, a site falls back to a faint outline with the built part rising through it. `tests/construction.rs` checks every building footprint and house size has its art.
  - These sprites live in the objects tile set's `overlays` category (`OBJECTS_OVERLAYS_CATEGORY`). Its tile defs have no specialized `TileKind`, so the palettes, `tiles.list` and `world.place` leave them out. The tile generator makes them (`catalog/overlays.json`).
- `game::world::World` ([world/mod.rs](crates/game/src/world/mod.rs)) — generational-arena `SpawnPool`s: one per building archetype, plus unit and prop pools. Iteration yields only spawned entries. `World` has a `locked` flag — during locked periods (e.g., mid-iteration) spawn/despawn is rejected. Must happen via deferred `SimCmds`.
- `game::tile::TileMap` ([tile/mod.rs](crates/game/src/tile/mod.rs)) — layered 2D grid (Terrain / Objects) with bitflag `TileKind`. **Route edits through `TileMap` wrappers** (`set_tile_flags`, `on_tile_def_edited`, etc.); they keep the pathfind `Graph` in sync. Direct edits bypass the graph update and will corrupt pathfinding.

### Deferred commands (important)

Mutation during update is routed through two queues so iteration isn't invalidated:
- `game::session::GameSessionCmdQueue` — session-level (quit, load preset, save game, reset map). Consumed once per `GameLoop::update`.
- `game::sim::SimCmds` — simulation-level (spawn tile/building/unit, despawn, callbacks). Uses a promise-style API (`spawn_*_promise` returns a handle you can poll later for `SpawnReadyResult`).

If you're tempted to mutate the world inside a system callback, queue it instead.

### Configs & singletons

- `game::config::GameConfigs` is a `#[serde(default)]` struct loaded from `assets/configs/game/configs.json`. Sub-configs: `engine`, `save`, `camera`, `sim`, `display` (the player's UI scale, colour-blind overlays, animated water), `debug`. Fields are auto-rendered in the debug UI via `#[derive(DrawDebugUi)]`.
- `assets/` is read-only at runtime. The player's changes to `GameConfigs` (the settings dialog, through `GameConfigs::save`; not in a script, a replay, the smoke test or a run with `--default-configs`: `GameLoop::saves_user_configs`) go to the user configs: only the values that differ from the defaults, as JSON, in `saves/user/configs.json` on desktop and under the key `heritage_builder/saves/user/configs.json` in the browser's localStorage on the web. `GameConfigs::load` reads the defaults and applies the user configs over them (objects merge key by key, other values replace; another variant of an enum with fields replaces the old one); `load_defaults` leaves them out, as the test harness and `--default-configs` do. Saving with nothing changed deletes the file. Code: `engine::config` (`configurations!` with `user_configs: "<name>"`), on the user-file functions in `save::storage`. `saves/user/` isn't listed as saves.
- Configs, tile sets, unit/prop/building configs are loaded once into `SingleThreadStatic` globals (`GameConfigs::load()`, `UnitConfigs::load()`, etc.) and accessed via `::get()`. Only the thread that called `load()` can read them; tests reuse the main thread for this reason.
- Minimap ([docs/plans/minimap.md](docs/plans/minimap.md), `tile/minimap/`): `model.rs` keeps a grid of terrain and cover per cell and a feature per building, updated by `TileMap`'s place, clear, move and tile-flag paths and rebuilt on load (`#[serde(skip)]`, no save data). Other sizes in points (the HUD's panels, the minimap, widgets' own widths) don't grow, so the HUD's text outgrows its panels at high scales: a full scale needs egui's zoom (`TODO(realm-ui)` at `skin::ui_scale`). A dialog that sizes its own contents (Settings, Custom Game, the campaign picker) scales them by `skin::dialog_ui_growth` (the UI scale, or less where the window caps the dialog) and its text, its buttons' included, by `skin::dialog_text_fit` (that over the UI scale), so they still fit from 75% to 200% on 1280 × 720; one whose contents scale with its content area (Home, About, the Game menu) takes `skin::dialog_content_scale` (that area's height over its height on 1920 × 1080 at 100%) for its sizes and `skin::dialog_content_text_scale` (that over the UI scale) for its text. `ui_menus.jsonl` checks them all at 75% and 200%.
- Fonts: `assets/fonts/`, static TTFs, one file per weight, each with its licence beside it, verbatim from upstream: `<font>_OFL.txt` (SIL OFL 1.1), and `fa_LICENSE.txt` for Font Awesome. The realm fonts are the mockups' (`docs/design/mockups/generator/common.py`, `REALM_FONTS`): Protest Revolution (Đại Long), Jaini with Spectral SemiBold for the Vietnamese letters it lacks (Kambara; the mockups' Spectral SC would draw lowercase ones as small capitals, since egui can't decompose a missing letter into Jaini's own with a combining mark, as a browser does), Amita Regular and Bold with Alegreya Medium and Bold (Tampadesa).
  - To add one: a static TTF, not a variable one (the google/fonts repository's static files under `ofl/<family>/`, or Google Fonts' `css2` API fetched with curl's default user agent, which serves static TTFs), named in lowercase (`spectral_semi_bold.ttf`), with its upstream `OFL.txt` as `<font>_OFL.txt`; then refresh `web/asset_manifest.json`. A font's metrics are the ones egui reads: the `OS/2` table's `sTypoAscender` and `sTypoDescender` if its `fsSelection` has `USE_TYPO_METRICS` (bit 7), else `hhea`'s ascender and descender. The descent is negative as stored; egui adds the line gap to the line height, and no text font here has one. A style's font `scale` is `units_per_em / (ascent - descent)`, its em over its line height: Protest Revolution 1000 / (960 + 240) = 0.8333.
  - A text style's `fallbacks` draw what its font lacks, glyph by glyph. egui centres a fallback glyph's line height on the font's instead of lining up their baselines, so give a fallback its font's `scale` and a `y_offset_factor` of half the difference of their `ascent + descent` (the ascent minus the descender's depth) in ems, the font's minus the fallback's: Kambara's Jaini (1048 / −266) and Spectral (1059 / −463) give ((1.048 − 0.266) − (1.059 − 0.463)) / 2 = 0.093.
  - Glyph test: `ui::check_glyph_coverage` ([ui/style.rs](crates/engine/src/ui/style.rs)) loads styles as the game does and lays out `ui::GLYPH_TEST_TEXTS` (Đại Long's names, every Vietnamese letter) in every text style but `icon`, and `ui::GLYPH_TEST_ICONS` in `icon`. It fails on a character none of the text style's fonts has, and on a letter or digit the style's monospace or icon font would draw (the first font in the chain that has it), since those draw it in the wrong face (punctuation and symbols may come from them). `cargo test -p game --test ui_skins` ([tests/ui_skins.rs](crates/game/tests/ui_skins.rs)) runs it on `menu::ui_style_sources()`, the developer UI's style and each realm skin's merged `style` block, and checks that Kambara's and Tampadesa's styles fail without their Vietnamese fallbacks; `cargo test -p engine --lib style` tests the check itself.
- 9-slice panels: a `UiNineSlice` ([ui/nine_slice.rs](crates/engine/src/ui/nine_slice.rs)) is a sprite and its borders in pixels (left, top, right, bottom), a `scale` (points per pixel, 0.5 for 2× art) and a centre that stretches, tiles (the last tile cut) or rounds (tiles resized so a whole number fit, as CSS `border-image-repeat: round`) (`UiNineSliceCenter`). The corners keep their size and shape; on a rect smaller than its borders they all shrink by one factor. Load one with `UiWidgetContext::load_nine_slice` (it reads the texture's size, `TextureCache::texture_size`), then hand it to `UiMenu::with_panel(panel, insets)`, `UiMessageBox::with_panel`, `UiTooltipText::with_panel(panel, insets)` or `UiTextButton::with_frame(UiTextButtonFrame)` (a panel per state, `_idle`, `_hovered`, `_pressed` and `_disabled` sprites), or draw it with `UiPainter::nine_slice(rect, &panel, tint)`, as one mesh. Stretched sprites (`with_background`) work as before. The Skin Gallery shows every skin panel, and the card panel with each centre and on a rect smaller than its borders; `cargo test -p engine --lib nine_slice` tests the quads.
- Realm UI widgets ([ui/widgets/](crates/engine/src/ui/widgets/), plan: realm-ui.md, Widgets to add): `UiTabBar` (tab_bar.rs; `UiTabLook::min_tab_width` and `min_tab_height`), `UiToggle` and `UiStepSelector` (choice.rs; `UiToggle::with_min_height`), `UiControlRow` (input.rs: a `UiSlider` or `UiDropdown` `with_row` as a settings row, its label at the left and the control at the right edge; `UiSlider::with_value_suffix`), `UiSeparator::with_color` (a plain line), `UiMenuItem` (menu_item.rs), `UiIconButton` and `UiTextButton::with_width(UiTextButtonWidth)` and `with_min_height` (button.rs), template rows `UiListRow`/`UiListRowLook` for `UiItemList::with_rows` (list.rs), `UiImage` (image.rs; fit contain, cover or stretch), `UiKeyValues`, `UiTable` and `UiMeter` (data.rs), `UiColumns` (columns.rs; fixed or fractional widths, each column measured at its own width), `UiCard` (card.rs; a panel around a widget group, picked by clicking it, its selected state read each frame, cards side by side sharing a `UiCardRow`'s height, its hover fill and pressed and disabled tints from `with_tints`) `UiRichText` (rich_text.rs; markup `*emphasis*`, `[name]colour[/]`, `[#rrggbb]`, or spans; `with_heading_font`, `with_letter_spacing`), `UiFrame` (frame.rs; a widget group on a 9-slice or fill with outlines, in a rect of its own size), `UiMapView` (map_view.rs; a texture map in a fixed rect: fit, wheel zoom about the cursor, edge pan, an overlay callback drawing through its `UiMapViewTransform`, a frame texture round it; `record_map_marker` records what the overlay draws) and `UiCanvas` (map_view.rs; a rect painted by a callback). `UiTable::with_bullets` puts a bullet before each row. `UiPainter::label` draws text at a baseline point (start, middle or end) in the theme's body or heading font, with letter spacing, a halo and a shadow (`UiLabelLook`); `dashed_polyline`, `dotted_polyline`, `dashed_circle`. They stay skin-agnostic: textures, `UiNineSlice`s and colours come from the caller (`skin::*` in the game). Interactive ones play their roles: tabs `tab_selected`, toggles `toggled`, menu items, cards and rows `item_hovered`/`item_selected`, step selectors `slider_changed`, icon buttons `button_pressed`. The Skin Gallery (Skins, above) shows every one in each realm's skin, and `ui_skins.jsonl` drives them.

### Realm and profile

- `game::realm::Realm` ([realm.rs](crates/game/src/realm.rs)): `DaiLong`, `Kambara`, `Tampadesa`, spelled `dailong`, `kambara`, `tampadesa` in configs, the profile and automation (strum and serde both lowercase). Each campaign in `campaigns.json` has an `id` (the profile's key; a missing one becomes `campaign_<index>` on load) and a `realm` (default `dailong`). Campaigns II (`temple_mountain`) and III (`ten_thousand_temples`) are there without missions until their game phases write them; the home menu and the picker show them as "coming soon". Realm names and campaign names are `Realm` strings (`realm.<realm>`, `campaign.<id>`, else the config's `name`: `CampaignDef::display_name`), and so are mission names: `mission.<campaign id>.<number from 1>`, else the mission's `name` (`CampaignDef::mission_display_name`).
- `realm::ui_realm()` picks the realm whose look the UI shows: the override from `ui.realm realm=...` wins; in game, the active campaign's realm, else the custom game's (`custom_game::active_realm`), else Đại Long; in the home menu, the latest campaign the profile has reached (in `campaigns.json` order), else Đại Long. `choose_ui_realm` is that decision as a pure function. `ui_realm()` asks `GameLoop`'s current session for the menus mode, which is wrong while a session's menus are built (in `GameLoop::start` and during a session switch), so code that builds menus, and automation commands, call `ui_realm_for(in_home_menu)` with the menus mode they work on. The minimap's style follows it.
- `game::profile::Profile` ([profile.rs](crates/game/src/profile.rs)): the player's progress across sessions, not part of `GameSession` (no save-version bump). Per campaign id a `CampaignRecord` (reached, the mission last started, missions finished, distinctions, finished, and `choices`: the site picked at each choice point, recorded by the world map's choice box (`Profile::choice_made`) and when a variant starts, and left out of the file while empty, so `PROFILE_VERSION` stays 1: older files read as before, though a build without the field reads a profile with a pick in it as broken and backs it up as below), `last_save` (what Continue will load) and `custom_realms`. It's the user file `profile`: `saves/user/profile.json` on desktop, localStorage on the web, written whole after each change (not an overlay). A missing file gives a fresh profile; a broken one or one of another `PROFILE_VERSION` gives a fresh one with a warning on the `profile` log channel; a run that writes the profile first copies that file to `saves/user/profile_unloaded.json` (if it can't, it leaves the file alone for the run), since the fresh profile replaces it at its first change.
- Loaded once in `GameLoop::start`, after the launch options and before the first session. `--fresh-profile` starts empty and never reads or writes the file. Script mode, replays and `--smoke-test-saves` read it but keep changes in memory, and the test harness never loads it (`profile::get()` is a fresh in-memory profile), so automation leaves no file behind. A recording holds the profile in its header, and the replay uses it, unless `--fresh-profile` is given (a warning says so when the recording's isn't empty); a recording without one, or with one that doesn't load, replays with an empty profile and a warning, never the local file's.
- Progress: the first campaign is always playable, the others once reached (`Profile::is_playable`, `playable_campaigns`); a campaign resumes at the first step it hasn't finished (a choice point counts as finished once one of its sites' missions is; World map data, below), at the site picked there if one was (else the choice point itself, until Phase 3's briefing offers the choice: `TODO(realm-ui)`), its first once all are (`next_mission`). The home menu's Campaign starts that (`campaign::start_mission`), or opens the picker when more than one is playable; Continue loads `last_save`, reading its mission for the subline from the save's header (`session::probe_save`; none for a save made before headers). `profile::revision()` goes up with every change.
- Custom games (`game::custom_game`, [custom_game/mod.rs](crates/game/src/custom_game/mod.rs); the dialog's in Dialogs above): `assets/configs/game/maps.json` (`MapConfigs`) lists the maps, each an `id` (the Menu string `map.<id>` names it), a `name` and a `source`: `Blank` (its default width, height and terrain), `Preset` (a debug preset; unlike `session.load_preset`, a custom game keeps the player's cheats and not the preset's) or `SaveGame` (a save's map, listed only while the save is in `saves/`), and the starting treasury's choices. Start queues `GameSessionCmd::StartCustomGame`: the session is replaced with the map, then `GameSession::start_custom_game` restarts the calendar at the date picked (the realm's eras: those of its first campaign in `campaigns.json` that has any), sets the treasury (`Finance::start_mission`) and the risks switch, and makes the game the active custom game (`custom_game::active`): its realm (the UI's in game, source `custom_game`), map, difficulty, fast construction and the stored switches. That's runtime state, not part of `GameSession`: a save writes it in its header (`realm`, `custom_game`) and a load reads it back (`ActiveCustomGame::from_header`: a game outside a campaign whose header has a `custom_game` record), so no save-version bump; any other session ends it. The preview bakes a blank or preset map with `crates/minimap_bake` in the realm's minimap style (`custom_game::preview`), in the world's isometric projection; a save's map shows the realm's emblem (TODO). `session.state` reports it under `custom_game`.
- Hooks: `GameSession::start_mission` marks the campaign reached, records the mission and unlocks its realm for Custom Game; `campaign::tick` queues a finished mission (`take_finished_missions`), which `GameLoop::update` records, and finishing a mission of a campaign's last step finishes it and reaches the next visible campaign (`next_visible_after`); a successful `GameSession::save_game` (the autosave and `session.save` included) sets `last_save`.
- World map data (`game::world_map`, [world_map/](crates/game/src/world_map/mod.rs); plan: realm-ui.md, Phase 2): one file per campaign, `assets/configs/game/world/<name>.json` (the campaign's `world_map`, else its id), loaded once after `campaigns.json` (`WorldMapConfigs::load`) and validated (ids, owners, references, the extent; errors logged on the `campaign` channel). In the mockup generator's map space (`extent` 1000 × 672, `docs/design/mockups/generator/common.py`): `powers`, `cities` (id, Realm name key, position, kind, owner realm or power, role, label side, `player` for one that's the player's from the start (the capital, monuments; not a city a mission will found), optional `subtitle` and static `trade`: relations 0–5, the route line, sells and buys with prices, the court's request), `routes` (kind, state, points, the cities they join), `labels` (realm, region or note, size and letter spacing in points at 1080p), `uncharted`, `threats`, `compass`, `choice_box`. Text in them is keys: names in Realm, route lines, carriers and goods (`trade_good.<id>`) in Menu. Missions in `campaigns.json` gain `id`, `city` (the city they found: id, name key, position) and `choices` (sites A and B, each a `name` key, a position, a `label` side and the mission it starts, by index or id: the choice point itself or a variant, a mission only a choice starts). A campaign plays its steps (missions that aren't variants: `CampaignDef::steps`); `Profile::next_mission`, mission numbers ("mission 2 of 3"), finishing a campaign and `advance_to_next_mission` go by steps. `WorldMapProvider` is what the screen reads (cities, routes shown once their cities are, the player's cities: the file's `player` ones, finished missions' and the current one's; a city's panel; the next mission's choice); `ConfigWorldMapProvider` reads the configs and the profile until M10's trade replaces the static values. A mission's city names the save header's `city_name` and the Game menu's place line. The map's base art, frame and background are the realm skin's `world_map` (Skins, above): the cities, routes, labels, threats (the skin's storm clouds at their position, then their words and arrow) and compass are drawn live over the base, at their positions times its `pixels_per_unit`. The base already holds the scenery: the uncharted areas' fill, hatching and dashed outline (a file's `outline` must match the art; only their `title` and `subtitle` are drawn, at `label`) and the sea traders' ships (which the routes drawn live cross, where the mockup draws the ships over them). `cargo test -p game --test world_map` checks the shipped files and that a known city lands on the base where the generator draws it; `crates/tools/ui-art/tests/test_world_map_art.py` checks every city against the generator.
- Hidden campaigns (`hidden: true` in `campaigns.json`, after every visible one, since saves name a campaign by index): never listed by the home menu, the campaign picker or Custom Game, never the home menu's realm, never reached by finishing another, left out of the numbering (`CampaignConfigs::visible`, `campaign_number`); `profile.set` reaches one, and `session.start_mission campaign=<id> [mission=<index or id>]` starts any campaign's mission (the profile's next if none is given). `test_choices` (on Campaign I's map), `test_choices_kambara` and `test_choices_tampadesa` (Campaigns II's and III's, with the mockups' choice sites) each hold a mission, then a choice point whose site B starts a variant. Kambara's and Tampadesa's first missions have no goals, so they're finished at once (MissionComplete opens); a choice point's `choice_text` (a Menu key, `{a}` and `{b}` the sites) words its box's line, and a site's optional `phrase` (a Realm key) its name in that line ("The {a} or the {b}" with "royal port"; the box's name widgets are `WorldMap/choice/<phrase>`). `session.state`'s `campaign` has `campaign_id`, `mission_id` (null without one) and `completed`.
- Commands: `ui.realm [realm=dailong|kambara|tampadesa|auto]` (the realm showing and its `source`: override, campaign, custom_game, profile or default; `auto` clears the override), `profile.state` (the profile, `ui_realm`, `writes_file`, `file`), `profile.set` (`reached`, `campaigns`, `last_save`, `custom_realms`, validated against the configs), `profile.reset` and `world_map.state [campaign=...]` (what the world map shows of a campaign: cities, routes, labels, panels, the next mission's choice). Tests: `cargo test -p game --test realm_profile`.

### Localized strings

- `engine::ui::text` ([ui/text.rs](crates/engine/src/ui/text.rs)): one file per language, `assets/configs/ui/text/<language>.json` (only `en.json` so far): an object of categories by name (`UiTextCategory`: `TileDescription` and `UnitDialog`, keyed by tile def and unit config name, then `Menu`, `Hud`, `City`, `Story`, `Realm`, `Messages`), each an object of keys. A value is its text, or plural forms (`{"one": "{count} month", "other": "{count} months"}`, CLDR names, `other` required). Every file is loaded at engine init and never dropped; `text::set_language` switches by name, and `text::version()` counts the switches, for UI that keeps text it looked up: the dialogs and the HUD rebuild when it changes (`dialog::sync`, `InGameMenus::sync_skin`; see Skins above), which closes the inspector and an open popup and drops the palette selection (Settings keeps its pending edits and Load / Save its typed name). The language comes from `GameConfigs::engine.language` (default `en`), set in Settings' Game tab (`MainSettings/Game/Language`); a replay applies its recording's.
- API: `text::get(category, key) -> &str`; `text::format(category, key, &[("name", value)])` fills `{name}` (`{{`/`}}` are braces); `text::format_count(category, key, count, args)` picks the plural form by the language's rule (`PluralRule`; English: 1 is `one`) and fills `{count}`; `text::find_str(category, hash)` for optional text by hashed key (the inspector's descriptions, by `TileDef::hash`). Lookups work on any thread, and load the files on first use when the engine didn't (tests).
- Fallback: a key the current language lacks shows in English, logged once per key; a key English lacks shows as the key itself, logged once and listed by `text.missing`. A missing or broken file is an error in the log, not a panic.
- Widgets take a `UiString` (`ui::text::UiString`, re-exported as `ui::UiString`): `UiString::key(UiTextCategory::Menu, "button.cancel")`, looked up each time it's drawn, or literal text (`&str` and `String` convert). The retained widgets' label and tooltip setters take `impl Into<UiString>` (buttons, tooltips, text labels, heading lines, inputs, lists, labeled groups); menu and popup labels stay plain strings, since they're automation ids, though a menu without a background sprite also draws its label as its title, so a screen like that needs a `UiString` title of its own when it's localized. Automation records the text as drawn, so English paths are unchanged.
- To add a key: add it to `en.json`, and name it as `UiTextCategory::<Name>, "<key>"` (the category spelled out, the key a literal right after it). `cargo test -p engine --lib text` scans every crate's sources for those pairs and fails on a key `en.json` lacks; it also fails on a language file with a key or placeholder `en.json` lacks, or a key given twice (the game logs that as an error and keeps the last).
- Commands: `text.language [language=...]` (report or switch; unknown is `NotFound`), `text.missing [reset=true]` (`count` and `missing` by category; `untranslated` by language), `text.get category=... key=... [count=...] [args={...}]` (no miss recorded). The developer Game Configs window's Ui Text tab switches the language and lists every key.

- `engine::ui::sound` ([ui/sound.rs](crates/engine/src/ui/sound.rs)): `UiSoundKey` names a sound by its role (`button_pressed`, `toggled`, `slider_changed`, `dialog_opened`, `popup_closed`, `notification`, `alert`, `tile_placed`, ...; snake_case in data and automation), each with its own flags and cooldown (`default_flags`, `default_cooldown`). ### Saves

- JSON via serde; the whole `GameSession` serializes.
- Saves are versioned: `GameSession::save_version` must equal `CURRENT_SAVE_VERSION` ([session.rs](crates/game/src/session.rs)). `load_save_game` probes the version before the full deserialize and refuses any mismatch.
- When a change alters the serialized layout so older saves no longer deserialize as-is:
  1. Bump `CURRENT_SAVE_VERSION`.
  2. Add `crates/tools/save-migration-scripts/v<N>_to_v<N+1>.py`, modeled on the existing scripts (idempotent, rewrites `saves/*.json` in place, rejects saves from older versions).
  3. Migrate the local `saves/`, run the smoke test, and regenerate `saves/sample_saves.zip` from the migrated files (entries are stored with their `saves/` prefix).
- Goods are saved by name, never by position: per-good arrays (`[_; RESOURCE_KIND_COUNT]`) go through `sim::resources::per_kind_map`, which writes `{ "Rice": 2 }`. So adding a `ResourceKind`, anywhere in the list, needs no save-version bump; removing or renaming one does. New per-good state must use `per_kind_map` too.
- The finance accounts are saved the same way, by category name (`sim::finance::per_category_map`): adding a `LedgerCategory` needs no bump.
- Config-derived state is refreshed on load: each building's `post_load` sets its stocks' accepted goods and capacities from its config again (keeping the goods held), so a config change reaches old saves. Follow that for new config-driven fields rather than trusting the saved copy.
- Save metadata ([save_header.rs](crates/game/src/save_header.rs)): a save file starts with `save_header` (campaign id and mission index, city name (none yet), realm, date ordinal and text in the realm's era, population, treasury, time played, local save time, and a custom game's `custom_game` record: its map and options), then the session's fields (`SaveFileContents`, written by `GameSession::save_game`). Every field is optional, so it isn't part of `GameSession` and needs no version bump; `session.checksum` hashes the session alone. A header this game can't read (a field of another type) reads as blank, with a warning, and the save still loads. `save_header::read_head` reads the version and the header from the first 16 KB without parsing the session, then the last 16 KB for the version the migration scripts append, then the whole file if neither has it; `session::probe_save` and the version check before a load use it. Time played is `GameSession::time_played_secs` (`#[serde(skip)]`): advanced by each frame's time step in game, seeded from the header on load. The save time is left out in script mode, recordings and replays (`save_header::set_wall_clock`), which keeps `determinism.json` the same across runs.
- Thumbnails: every save made in game (the autosave and `session.save` included: `GameSession::save_game_with_thumbnail`) captures that frame's scene without the UI as `saves/<name>.jpg`, cut to `SaveGameConfigs::thumbnail_size` (320 × 180; `ScreenshotScale::Cover`, `ScreenshotFormat::Jpeg`), encoded in the frame. `engine::save::storage::delete_save_file` deletes it with the save, and a save that writes no new one (made in the home menu, or whose capture failed) deletes the old one (`save_header::remove_stale_thumbnail`). The autosave timer pauses while the Load / Save dialog is open and goes on from where it stopped once it closes. None on the web (`save_thumbnail_path` is None there; `TODO(realm-ui)`). Commands: `session.save_info name=...` (exists, loadable, header, `has_thumbnail` and its path, those two also for a missing save) and `session.delete_save name=...`.
- Don't add `#[serde(default)]` to save-state fields as a compatibility shim. Save format v2 deliberately removed those shims because they risk silent corruption. `#[serde(skip)]` is still right for runtime-only state that is rebuilt in `post_load` (e.g. the pathfinding graph on `TileMap`).

## Conventions

- `#![allow(dead_code)]` is set crate-wide in `game` and `engine` — dead-code warnings from the compiler are silenced there.
- Many hot data structures prefer stack allocation: `arrayvec`, `smallvec`, `small-map`, `smallbox`, `slab`, `bitvec`. Prefer these over `Vec`/`HashMap` when capacity is bounded.
- `#[enum_dispatch]` is used for polymorphism over variant sets (e.g. building archetypes) instead of `dyn Trait`.
- Global state goes in `common::mem::SingleThreadStatic` (or `Singleton` / `SingletonLateInit` and their `singleton!` / `singleton_late_init!` macros), not `thread_local!`: the game is single-threaded, and these cost no TLS lookup while asserting, in desktop debug builds, that only the first thread to touch them ever does. Keep `thread_local!` for state that other threads really reach, such as the logger's `IS_DISPATCHING` (logs come from worker threads too). A crate's own `#[test]` unit tests run one per thread under libtest, so a global they touch panics there: keep such state on its owner instead (as `Finance` keeps its debt notices, `#[serde(skip)]`).
- Bitflag types are declared with the `bitflags_with_display!` macro from `common` so they format nicely in logs and debug UI.
- Use `engine::log` (channel-based logger), not `println!` / `eprintln!`, except in tools/bundler and for script mode's result lines, which are the run's machine-readable output on stdout (`game::automation::script`).
- The engine's path types (`FixedPathBuf`/`FixedPath`/`AssetPath`/`PathRef` in `engine/src/file_sys/paths.rs`) differ from `std::path`: `join`/`push` with a path that starts with a separator appends it instead of replacing the base.
